# Plan 02-01: Custom Agent API Routes (Manifest Sync & Atomic Batch Sync)

<threat_model>
- **Threat:** Unauthenticated or unauthorized actors calling collection sync endpoints to harvest client details or falsely credit installments.
  - **Mitigation:** Enforce strict role validation middleware requiring valid Bearer auth token and `role = 'agent'` on all `/api/agent/*` endpoints (SEC-04).
- **Threat:** Incomplete or partial batch updates during network drop leaving financial records in an inconsistent state.
  - **Mitigation:** Wrap all installment status updates in `POST /api/agent/batch-sync` inside a database transaction (`$app.dao().runInTransaction`) ensuring all-or-nothing atomicity.
- **Threat:** Replay attacks re-submitting offline payment batches to produce duplicate receipts or distorted collection counts.
  - **Mitigation:** Verify `idempotency_key` against existing installment records; gracefully skip duplicate entries while processing fresh ones.
</threat_model>

## Objective
Implement custom PocketBase API endpoints in `pb_hooks/04_agent_api.pb.js` for morning manifest download (`GET /api/agent/sync-manifest`) and atomic offline collection batch synchronization (`POST /api/agent/batch-sync`) with strict role-based access control.

<task>
<name>Implement Morning Manifest Sync Route (GET /api/agent/sync-manifest)</name>
<read_first>
- PRD.md (Section 5.2: Offline Synchronization Lifecycle)
- .planning/phases/02-agent-pwa-core/02-RESEARCH.md (Section 1.2)
</read_first>
<action>
In `pb_hooks/04_agent_api.pb.js`, register `GET /api/agent/sync-manifest`:
1. Authenticate agent.
2. Query all `subscriptions` where `agent_id = auth.id`.
3. Query all `installments` for those subscriptions where `status IN ('pending', 'overdue')`.
4. Query active `packages` data.
5. Return JSON payload: `{ subscriptions, installments, packages, synced_at }`.
</action>
<acceptance_criteria>
- `GET /api/agent/sync-manifest` returns JSON containing `subscriptions`, `installments`, and `packages`.
- Returned subscriptions and installments only belong to the authenticated agent.
</acceptance_criteria>
</task>

<task>
<name>Implement Atomic Batch Sync Route (POST /api/agent/batch-sync)</name>
<read_first>
- PRD.md (Section 5.2: Step 9 & 10)
- GEMINI.md (Business Rule 4: Offline sync idempotency)
- .planning/phases/02-agent-pwa-core/02-RESEARCH.md (Section 1.3)
</read_first>
<action>
In `pb_hooks/04_agent_api.pb.js`, register `POST /api/agent/batch-sync`:
1. Authenticate agent.
2. Extract `items` array from request body.
3. Run transaction using `$app.dao().runInTransaction((txDao) => { ... })`.
4. For each item:
   - Check if `idempotency_key` already exists.
   - If duplicate, record as skipped.
   - If valid, find installment record, verify it belongs to agent's subscription, update `status = 'paid'`, `payment_mode`, `paid_at`, `receipt_slip_id`, `idempotency_key`, `collected_by = auth.id`, `handover_status = 'agent_custody'`, and save via `txDao.saveRecord(record)`.
5. Return JSON: `{ success: true, processed_count, skipped_count, results }`.
</action>
<acceptance_criteria>
- `POST /api/agent/batch-sync` processes a batch of offline payment records atomically.
- Records updated in the batch have `status = 'paid'` and `handover_status = 'agent_custody'`.
- Duplicate idempotency keys are handled idempotently without throwing unhandled exceptions.
</acceptance_criteria>
</task>
